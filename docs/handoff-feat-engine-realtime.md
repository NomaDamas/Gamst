워크트리 `.local-run/wt-timeline`, 통합 브랜치 `37a3c05`에서 분기. push와 PR은 하지 않았습니다.

## 1. 레코드마다 창 전체를 다시 집계하던 것

- 찾은 것: 레코드마다 세 가지가 돌았습니다. (a) 창 안 최신 신호(`latest_signals`, JSON을 모두 다시 풂) (b) 숫자 신호 평균(`numeric_summary`, 남아 있는 **모든** 신호를 훑음) (c) `ContextMemory` 크기 다시 세기.
- 등록된(capability) 레코드는 값이 항상 object라 숫자 평균을 바꾸지 않습니다. 하지만 모든 레코드가 `human.inference` 레코드를 하나씩 만들고, 그 내용(모달리티, 품질, 모델, 추세)이 (a)와 (b)를 씁니다. 그래서 빼지 않고 싸게 만들었습니다.
- 방법: 연결마다 메모리에만 있는 색인(`temp` 테이블과 트리거, 파일에는 쓰지 않음). SQLite가 같은 트랜잭션 안에서 추가·삭제·되돌리기를 맞춥니다. 다른 연결이 파일을 쓰면(`PRAGMA data_version`) 다시 만듭니다.
- 같음 확인: 무작위 순서(퇴출, 보존 기간, 삭제, 실패한 쓰기, 수정, 철회, 뒤바뀐 시각, 다른 연결)에서 예전 SQL과 **비트까지** 같습니다(평균 포함). 엔진이 낸 모든 레코드, `get_trends`, `get_context`도 예전 방식과 같습니다.
- 실측(등록 레코드, 메모리 저장소, 600/1200/1800개 구간, 레코드당): 2.77 / 7.73 / 12.5ms → 0.34 / 0.34 / 0.35ms. 숫자 신호를 섞으면 3.6 / 9.7 / 15.0 → 0.37 / 0.41 / 0.43ms. 파일 저장소: 4.7 / 11.9 / 17.5 → 1.7 / 2.2 / 1.9ms.
- `get_context`(60초 창, 10,000개): 62ms → 0.4ms. `Store.add`: 22 → 40us(색인 유지), 매번 지울 때 29 → 54us.
- 남은 것: 숫자 평균은 남아 있는 숫자 신호 수에 비례합니다(5,000개 1.2ms, 20,000개 5.2ms. 예전 21.7 / 89ms).

### 레시피의 `sensor_inference_interval_ms=1000`

비용 때문에는 더 필요 없습니다. 하지만 **남겼습니다**: 레코드마다 저장되는 `human.inference`가 보존 한도를 절반 나눠 씁니다(1,800개 커밋에 3,600개 저장, 4.8MB. 켜면 1,801개, 2.1MB). 주석을 바꿨습니다. 없애려면 `gamst/recipes/__init__.py` 한 줄입니다.

## 2. `get_timeline`이 이벤트 루프를 막던 것

- 저장소 조회만 루프에서 200개씩 나눠 하고, 레코드 풀기와 행 계산은 스레드에서 합니다. 읽기를 시작한 뒤에 배운 레코드는 들어가지 않으므로 한 시점의 상태입니다. `:memory:`와 파일 모두 같은 방법입니다(두 번째 연결을 쓰지 않으므로 쓰기가 잠기지 않습니다).
- 레코드를 풀어 놓지 않고 텍스트로 들고 있습니다. 풀어 놓으면 쓰레기 수집 한 번이 106ms를 멈췄습니다.
- 읽는 중에 데이터를 지우거나 닫으면 결과를 버리고 오류를 냅니다.
- 실측(10,000개, 30fps Pipeline, 읽기 15번): 루프 최대 멈춤 8ms, 프레임 간격 최대 37.5ms. 예전에는 읽는 시간 전체(최대 529ms), 이어서 읽으면 합쳐져 1,790ms였습니다. 1,000개: 165ms → 3.8ms.
- 읽는 시간도 줄었습니다(10,000개 첫 쪽 430 → 204ms, 기본 131 → 35ms).
- `count_events`, `inspect_interval`은 그대로 루프에서 돕니다.

## 3. Pipeline

- `complete_from_ms`(첫 프레임, 나중에 켜거나 추가한 모듈은 그때부터), `holding_from_ms`(모듈의 `pending_since_ms`)를 `status()`에 냅니다.
- 시각이 다른 기록을 이어 줄 때도 `clock_id`/`clock_epoch`를 유지합니다.
- `asr_words`: 엔진이 partial을 내면 그 발화의 시작부터 `pending_since_ms`입니다(partial을 내보내지 않아도).
