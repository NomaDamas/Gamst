## C. 승인된 설계 보고 1: 최신 실시간 모델 장착 (원문)

## 0. 현재 상태

- **GCP:** VM이 켜져 있고, Qwen3.5-9B(고정 커밋 `c202236`)와 이 모델을 지원하는 vLLM 0.34 설치가 끝났습니다. VM은 최대 7시간 뒤 자동으로 정지됩니다.
- **이미 있는 연결 코드:** GAMST 저장소에 최신 모델용 연결 코드(어댑터)가 이미 많이 있습니다. 예: RF-DETR, SAM 3.1, Video Depth Anything, Qwen3-ASR, CED. **다만 대부분 "실제 가중치로는 아직 검증 안 됨" 상태**라 연결 검증부터 해야 합니다.

## 1. 바뀐 구조

```
카메라 ─→ Qwen3.5-9B (스트리밍 VLM)          → 장면 의미 상태 (1초마다)
       ├→ SAM 3.1 / RF-DETR / YOLOE          → 사물·사람 ID 추적 (마스크, 박스)
       ├→ Video Depth Anything               → 깊이 → 실제 거리(m)
       ├→ 자세·손 추정                         → 관절, 손 위치
       └→ rPPG 모델 (EfficientPhys 등)        → 맥파
마이크 ─→ CED (소리 사건: 끓음·깨짐·비명…)
       ├→ Qwen3-ASR + VAD + 화자 분리 + 말하는 사람 찾기 (TalkNet)
       │                                    → 누가 언제 무슨 말을 했나
센서 ──→ IMU / 이벤트 카메라 / 깊이 카메라    → 가속도, μs 타이밍
              ↓  (모두 같은 시계로 정렬)
GAMST: 능력 provider (횟수 / 물리 / 리듬 / 확률 구름)
     + Fusion → Semantic State Chain → 사건 기록 (근거 ID 포함)
              ↓
           MCP Context
              ↓
   Gemini 3.1 Pro (Strong VLM + LLM) ← 사용자 질문이 올 때만 1번
```

## 2. 능력별 최대화 설계

### ① 확률 구름: 사용자 규칙 → 위험이 쌓였다 식는 알람

| 근거 | 연결 모델 | 기존(경량)과의 차이 |
|---|---|---|
| 누가·무엇이 | SAM 3.1 텍스트 프롬프트 ("아이", "가스레인지", "냄비") | 원하는 대상을 이름으로 지정하고 ID로 계속 추적 |
| 실제 거리 | Video Depth Anything + 추적 결과 | 화면상 거리 대신 **미터 단위 3D 거리** |
| 접근 예측 | 거리 변화 → 속도 → **"2초 후 도달" 예측** | 위험해지기 **전에** 알림 |
| 행동 | 자세·손 추정 | "손이 냄비 손잡이로 향함" |
| 소리 | CED 소리 사건 | "물 끓음", "유리 깨짐", "비명" |
| 말 | Qwen3-ASR | "뜨거워!", "도와줘" |
| 장면 의미 | Qwen3.5-9B 상태 | "아이가 의자를 끌고 감" 같은 맥락을 근거 점수로 |

계산은 지금 만든 RiskField 그대로입니다. 근거가 쌓이면 올라가고, 없으면 시간에 따라 식고, 켜짐·꺼짐 기준을 따로 둬서 깜빡이지 않습니다. 근거 항목만 늘어나고, 알람마다 **"왜 켜졌는지"(기여한 근거)**가 남습니다.

### ② 순간 포착 + 물리

| 측정 | 연결 모델 → GAMST 계산 |
|---|---|
| 점프 높이·체공 | 자세(발) + 깊이로 실제 크기 측정(키를 가정할 필요 없음) → 포물선 맞춤 |
| 공 속도·궤적 | SAM 3.1 추적 + 깊이 → 3D 속도, 착지 예측 (기존 kinematics, physical_state 코드) |
| 충돌의 물리량 | 충돌 직전 속도 + **소리 onset으로 접촉 시각을 ms 단위 정렬** |
| 아주 빠른 순간 | 이벤트 카메라(OpenEB)가 있으면 μs 타이밍 |

말씀하신 대로 "충돌이 났나?"는 Gemini가 나중에 천천히 판단하면 됩니다. GAMST는 **물리량과 시각**만 맡습니다.

### Count

- **심박:** 신경망 rPPG 모델로 교체합니다. 현재 어댑터는 EfficientPhys인데 최신 SOTA는 아니라서 후보를 다시 고릅니다.
- **호흡:** 가슴 움직임(자세·광학 흐름)과 숨소리, 두 경로를 합칩니다.
- **떨림:** 손 관절 주파수로 측정합니다.

### 기억

| 질문 | 답하는 데 쓰는 근거 |

## D. 승인된 설계 보고 2: Watch 트리거, B·C 평가, 병렬 실행 (원문)

Gemini 3.1 Pro 단독(A)은 다시 돌리지 않고 B와 C만 합니다. 필요한 모델은 큰 GPU 한 장에서 동시에 병렬로 돌리고, 트리거는 사용자나 jev가 직접 정한 조건으로만 작동하게 바꿨습니다. 대기 중이던 L4 VM은 비용을 아끼려고 정지해 두었습니다(Qwen3.5-9B와 vLLM 설치분은 디스크에 남아 있습니다).

## 1. 트리거: MCP "Watch" 구조

트리거는 GAMST가 알아서 판단하는 만능 규칙(silver bullet)이 아닙니다. **명시적으로 등록하고 고칠 수 있는 조건**입니다.

```
사용자 또는 jev ──(MCP 도구: create_watch / update_watch / delete_watch / list_watches)──→ GAMST
                                                                                   │
GAMST: 병렬 모델 신호를 시간 정렬 → 조건을 매 순간 계산 (확률 구름 등, 모델 호출 없음)
                                                                                   │ 조건 충족
                                                                                   ↓
MCP 알림 → 등록된 수신자(Gemini 또는 앱)에게 "사건 + 그 전후 시간 Context" 전달
```

| 항목 | 설계 |
|---|---|
| 조건을 정하는 쪽 | **사용자:** 자연어 → 규칙으로 변환 → 화면에서 확인한 뒤 등록<br>**jev(앱 쪽 판단 에이전트):** 작업 중 필요하면 MCP 도구로 Watch를 직접 등록·수정 |
| 조건 형태 | 확률 구름 규칙(근거별 가중치·감쇠·켜짐/꺼짐 기준), 수치 임계값, 횟수, 순서 조건 |
| 전달 내용 | 사건, 근거 ID, 해당 시간대 타임라인. 예: "12.31초 아이가 가스레인지 0.8m, 12.40초 끓는 소리 0.92, 12.50초 손이 냄비 쪽" |
| 비용 통제 | 같은 Watch는 쿨다운을 두고 분당 최대 전달 횟수를 정합니다. **이 값은 Watch를 만든 쪽(사용자·jev)이 정합니다.** |
| 투명성 | 조건마다 버전(해시)을 남깁니다. 켜짐, 꺼짐, 억제 내역과 근거별 기여도를 기록해 오알람을 보고 직접 고칠 수 있습니다. |
| 조정 | 사용자가 "이건 오알람"이라고 표시하면, jev가 수정안을 **제안**합니다. 실제 변경은 명시적인 update 호출로만 하고 기록이 남습니다. |

GAMST에는 숨은 트리거가 없습니다. 조건 계산만 GAMST가 하고, 조건의 주인은 사용자와 jev입니다.

## 2. 평가: B와 C만

| 비교군 | 구성 |
|---|---|
| B. Qwen3.5-9B 단독 | 최근 프레임 sliding window로 직접 답합니다. 알림은 1초마다 "그 일이 일어났나?"를 직접 판단합니다. |
| C. GAMST 전체 | 모든 모델을 병렬로 돌리고 → GAMST → MCP로 넘깁니다. 알림은 Watch로, 질문은 MCP Context를 받은 모델이 **한 번** 답합니다. |

**C에서 질문에 답하는 모델은 정해 주셔야 합니다.** 기본안은 Gemini 토큰을 아끼는 쪽입니다.

| 선택지 | Gemini 토큰 | 의미 |
|---|---|---|
| **C-local (기본안)** | **0** | Qwen3.5-9B가 MCP Context를 받아 답합니다. B와 같은 모델이라 **차이는 GAMST Context뿐**이어서, GAMST의 효과만 깔끔하게 비교됩니다. |
| C-Gemini | 질문당 약 2~5천 (텍스트만) | 승인해 주시면 일부 샘플만 상한을 정해 돌립니다. 이미 있는 A 결과와 비교할 수 있습니다. |

Gemini 3.1 Pro 단독 결과는 이미 있으므로, 표에는 그 숫자를 그대로 참고용으로 넣습니다.

## 3. 병렬 실행: 큰 GPU 한 장 + GamstCrew

**GPU 할당량 상황 (방금 확인):**
- 프로젝트 전체 GPU 한도는 **1장**입니다.
- L4는 리전마다 1장, A100은 0장입니다. H100과 RTX PRO 6000은 별도 할당 신청이 필요합니다.
- **핵심:** 모든 모델을 GPU **한 장**에 올리면 "전체 1장" 한도는 그대로 둬도 됩니다. **큰 GPU 종류 할당 1장만 신청**하면 됩니다. 예전에 거절된 "L4 2장" 요청보다 작은 요청입니다.

**동시에 올릴 모델과 GPU 메모리 (추정치, 실제 측정 예정):**

| 모델 | 역할 | 메모리 |
|---|---|---:|

**GamstCrew의 역할 (이미 이런 용도로 만든 런타임입니다):**
1. **모델별 격리 실행:** 모델마다 버전을 고정한 별도 프로세스로 실행합니다. 의존성 충돌이 없습니다(vLLM 버전 충돌이 이번에 실제로 났던 문제입니다).
2. **GPU 메모리 예산:** 모델마다 메모리 몫을 정합니다. 한 모델이 넘치면 나머지를 보호합니다.
3. **같은 프레임, 같은 시계:** 카메라·마이크 입력을 공유 메모리로 **모든 모델에 동시에** 보냅니다. 모든 결과에 촬영 시각이 붙어 GAMST로 들어갑니다.
4. **실시간 감시:** 모델마다 처리 속도와 지연을 실시간으로 기록합니다. 밀리면 버린 프레임 수를 숨기지 않고 기록합니다.

**할당이 거절되면 (타협 없이):**
- 같은 GamstCrew 구성을 그대로 들고, H100을 바로 빌릴 수 있는 다른 클라우드(Lambda, RunPod 등)로 옮깁니다.
- "모델을 하나씩 순서대로 돌리는" 방식으로 바꾸지는 않습니다.

## 4. 실제 가중치 검증 원칙

| 단계 | 내용 |
|---|---|
| 1 | 고정 버전 가중치를 실제로 받아서 로드합니다. 받은 파일의 sha256을 확인합니다. |
| 2 | 실제 영상 클립으로 실행하고, 출력이 공식 데모와 맞는지 확인합니다. |
| 3 | 실시간 속도를 측정합니다. "실시간보다 느리지 않다"를 숫자로 보입니다. |
| 4 | 1~3을 통과하지 못하면 공식 패키지를 그대로 쓰거나 상용 API로 대체합니다. 예: 음성 인식을 클라우드 API로. 이때는 비용과 데이터 외부 전송을 표시합니다. |

## 5. 순서

1. **(정해 주실 것)** GCP에 RTX PRO 6000 1장 할당 신청 (안 되면 H100) + C의 답변 모델 선택 (기본안: C-local, Gemini 토큰 0)
2. 할당이 나오는 동안: 모델마다 실제 가중치 검증을 하고, GamstCrew 병렬 구성과 MCP Watch 도구를 구현합니다.
3. 큰 GPU에 모든 모델을 동시에 띄우고 실시간 속도를 측정합니다.
4. B와 C 평가를 진행합니다. 순서는 **확률 구름(MOT17) → 말과 기억(StreamArena) → 횟수(RepCount) → 심박(MCD-rPPG)**입니다. 점프와 "사람 + 소리" 확률 구름은 직접 촬영해서 합니다.
5. 결과를 보고하고 VM을 정지합니다.
