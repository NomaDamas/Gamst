## One word by one person in a 54 s clip of several people in a shop

There is no certain reference: nobody listened. From voice scores and lips: 7 utterances by the person are clear
(11.6, 12.5, 22.0, 28.0, 37.7, 46.2, 47.5 s), 2 likely by the lips (19.4, 19.7 s), about 4 undecided (20.1-20.4, 21.0, 24.0 s).

| setting | counted |
|---|---|
| before: 3 s windows, gate before ASR, Whisper small | 0 (`--without voice`: 2 of anybody) |
| after, Whisper small, speaker threshold 0.35 | 7 |
| after, Whisper large-v3-turbo, speaker threshold 0.35 | 8: 6 of the 7 clear ones + 21.0 + 24.0; misses 28.0 (voice score 0.27), 19.4 and 19.7 (0.18, 0.24) |

At the default threshold (0.5) only utterances above 0.5 count. 0.35 was chosen from the gap seen in this clip
(most of the person's words 0.40-0.57, others mostly below 0.28). The voice was enrolled from another recording of the person (120 s).

What was wrong and is fixed: a file given to `--kind voice` used only its first 1.5 s; fixed windows cut words; one verdict
covered a window shared by several people (now each word is scored with 1.5 s around it); the gate muted words before they were read.

Not fixed: an excited voice scores low; a word said off camera by a voice the model cannot place stays undecided. Lips
(active-speaker detection) decided two such cases by eye and are not a GAMST module.

### The owner's corrections (2026-11-26, by listening)

The person said the word at 12.0, 14, 19.7, 20.1, 21.5, 22.3, 28.1, 38.2, 46.6 and 47.7 s (10; times as shown when a word ends).

Missed 14.0 (not transcribed), 19.7 and 20.1 (voice scores 0.18 and 0.24), 28.1 (0.27); wrong 12.6 (0.42, another voice), 24.7 (not said).

Overlapping voices are the likely cause, not the size of the model.

The voice embedding alone does not separate these people on this audio; faces and lips are the next evidence (not built).
Separating overlapping voices first (PixIT, SepFormer) and hosted identification (pyannoteAI) did not count reliably
better: [overlap-2026-11-26.md](overlap-2026-11-26.md).

Speed (recorded input, whole recipe): small 34-45 s, turbo 90-117 s for 54 s of sound: turbo is not realtime on this CPU.

## Slams in real time (2026-11-27, Mac, Apple silicon, 32 GB)

The slam clip again (`testbed/b.mp4`, 11.9 s, 60 fps, 714 frames), text rule `hit_10_3.json`, truth `truth_hit.json`
(16 slams, matched one to one by end time within 0.2 s). Runs: `try-it/testbed/slam/rt.sh` (reports, logs and
`NAME.score.json` beside it, scored by `score.py`), one at a time under `guard.sh`. **Latency** is the word-to-HUD
equivalent: the capture time of the slam's end (the event's `end_ms`) to the moment the Store knew the count (L1: when it
was committed; final: when its revision, or the added count, was committed); the HUD draws what the Store holds.
**Memory** is the peak of the summed RSS of the run's process tree, sampled every 0.5 s; the GPU processes' Metal and
shared-memory pages count in each process, so it overstates (a CPU-only run: 574 MB). Nothing here is a held-out accuracy:
one clip, also used to choose.

Before (coordinator, 2026-11-27): `--as-live` with MediaPipe full on the CPU counted 14 of 16 and lost 190 frames in 10
gaps ("lane pose needs 33 ms per frame, camera gives one every 17 ms"); every frame processed: 16/16, 28.5 s.

### No person in the frame (맨까송 fades to black at 63.56 s)

The run gave the pose module up: `pose failed 25 times in a row ... provider worker is closed`, 108 frames (63.56 s to the
end) declared `error`, the run incomplete. Cause, reproduced on a black 1280x720 frame (`black.py`): YOLOX-m's NMS tail
has shapes that depend on how many boxes it finds; with none, ONNX Runtime's CoreML execution provider refuses the
zero-sized tensor (`Input (_1464) has a dynamic shape ({-1}) but the runtime shape ({0}) has zero elements. This is not
supported by the CoreML EP`); the worker answers the error and its stream closes (fail closed), so every later frame
fails too. ONNX Runtime CPU answers `[]` for the same frame.

Fix: the detector session asks CoreML for static input shapes only (`RequireStaticInputShapes`): CoreML runs the backbone,
the CPU the NMS tail. Measured on 9 frames of 맨까송 (5-65 s) and a black frame (`static.py`): the same boxes as CPU and
as the old CoreML session on every frame with people (1-4 boxes, equal to 0.1 px), `[]` on 63.6, 64.0, 65.0 s and black;
27.1 ms per detection against 27.5 ms (CPU 226.9 ms). The whole 맨까송 clip through `RTMWModels` on CoreML
(`extract.py`, detector every 500 ms, batches of 8): 2013 frames, 4665 poses, 108 frames without a pose (from 63.56 s),
no error, 69 s. Real-model test `test_rtmw_on_frames_without_a_person` (`GAMST_TEST_RTMW`, CoreML): fails on the old
code, passes now.

### Post mode lost 608 frames (관제탑, `cand_loose`)

`--timing post` gave up 608 frames (299.6-320.1 s) as `backlog`: `video_memory` dropped them at its disk bound
(4.13 GB = free disk minus the 5 GB floor), though at most 55 MB were spilled at any time (`max_spilled_bytes`). Two
causes: (1) post kept the pose lane's frames in the video memory as realtime does; the reader already waited for the
lane, but the L2 pre-roll (`max_lookback_ms`, about 85 frames) filled the 256 MB memory, so every new frame went to the
spill file; (2) the spill file only appends and is emptied only when no frame is spilled; with a pre-roll there always
was one, so it grew by every frame until the bound.

Fix: post (a recording that is not paced) never uses the video memory or L2: a `backlog="spill"` lane is an ordinary lane
the reader waits for (at most a batch waiting, the frames held in memory), so the file is read at the pace of
processing; `post_chunk_ms` is removed (it measured no gain, `pc60_1`). For realtime, the spill file writes a frame
into the place of one the lane is done with, so it is as large as the most frames spilled at once.
Tests: `PostMode` (3,000 frames, a slow stand-in, a video memory that can keep nothing: every frame processed once and in
order, 0 gaps, 0 frames in the video memory, no L2, the reader at most 17 frames ahead); `test_a_released_place_in_the_file_is_written_again`
(400 frames, always one spilled: the file stays at 2 frames, 0 dropped). Both fail on the old code.

Real run `post_gwan_1` (`try-it/testbed/fix3/post.sh`, RTMW-l CoreML, `--without target_person`, rule `rt_rule.json`,
`GAMST_SPILL_FLOOR_GB=5`): **15,670 of 15,670 frames processed, 0 lost, 0 gaps, 0 errors, complete**; no video memory
was made (`video_memory` null: nothing spilled), no L2 interval; 1,960 pose calls of 8 frames; pose latency p50 27.0 /

## Where a run's input began (2026-11-28, PR #373)

Each run now commits one `pipeline.input_start` event (capability `pipeline.inputs`) per input, at its first frame:
`start_ms` (that frame's capture time), `source` (`video_file`, `audio_file`, `sound_track`, `camera`, `host`, or the
class name of another source), `name` (a file's name, never its folder), `fps` and `frames_in_source` (as the container
says), `sample_rate` for sound, `live`, `paced`, `offset_ms`, and `position_ms`: where that frame is in its recording
(null for a live source). A capture time t is then `position_ms + t - start_ms` ms from the start of the video. MCP
`get_pipeline` shows it as `inputs.<id>.start`, `get_timeline` as `input_starts` (what was known at `as_of_ms`); it is
not a timeline column. Derived inputs (a module's joints) have none. Tests: `tests/test_timeline.py` `InputStartTest`,
`VideoFileStartTest` (a 40-frame 20 fps file read from 1 s: `position_ms` 1000, `frames_in_source` 40). The real
`p60_raw` report shows it under `pipeline.inputs.camera.start`: `source` `video_file`, `name` `b.mp4`, `fps` 60,
`frames_in_source` 714, `position_ms` 0.
